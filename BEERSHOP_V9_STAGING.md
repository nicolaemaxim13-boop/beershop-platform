# BeerShop v9 — staging-аудит готовності до продажів

**Стан:** тестова GitHub-гілка \`staging/beershop-v9-sales-readiness-audit\`.
**Production:** гілка \`main\` і чинний Render \`beershop-preview\` залишаються без змін.
**Немає:** реальних платежів, нових платних інфраструктурних компонентів, копіювання реальних замовлень до тестової БД.

## Що реалізовано

- \`GET /api/admin/v9/readiness\` — захищений лише для читання. Відповідь **не містить** персональних даних покупців, номерів рахунків, секретів або ідентифікаторів транзакцій.
- Вкладка **Готовність v9** в \`/manage\`. Можна переглянути вимоги до безпеки, цін, складу, реквізитів IBAN, відновлення та правових документів.
- Перевірка структури **українського IBAN** (29 символів, \`UA\` + цифри, ISO 13616 mod 97). Це **не перевірка власника рахунку, реквізитів банку або зарахування коштів**; додаткова перевірка обов'язкова.
- Якщо IBAN або назва отримувача некоректні, формування нового рахунку через \`/api/admin/orders/{id}/invoice\` завершується 503, а не показом хибного рахунку.
- Заголовки захисту \`X-Frame-Options\`, \`Referrer-Policy\`, \`X-Content-Type-Options\`, \`Permissions-Policy\`. Адміністративні відповіді мають \`Cache-Control: private, no-store\`; HTTPS отримує HSTS. CSP із блокуванням inline-script **ще не встановлено**, оскільки наявна адмінпанель використовує inline JS.
- Два **опціональні** staging-перемикачі, вимкнені за замовчуванням:
  - \`BEERSHOP_V9_DISABLE_ORDER_CREATION=1\` повертає HTTP 503 для нових замовлень — не здійснює тестові продажі.
  - \`BEERSHOP_V9_REQUIRE_QUOTE_TOTAL=1\` відмовляє HTTP 428, коли покупець не підтвердив \`expected_total\`. Існуючі браузери, які передають \`expected_total\`, працюють без змін.
- Всі API-тести виконуються локально на GitHub Actions у **SQLite або PostgreSQL з синтетичними даними**, не в Neon production.

## Важливі реальні блокери

1. **Власний рахунок та договір ФОП:** IBAN-перевірка підтверджує лише формат і контрольну суму. Дані банку, податковий режим і документальна відповідність залишаються обов'язком оператора.
2. **Ціни:** ручна валютна політика має бути актуальною (до 24 год) та явно активованою. Офіційний курс НБУ не дорівнює купівельному курсу банку. Формула не покриває ЄСВ, повернення, пакування та інші фіксовані витрати.
3. **Фізичний склад:** \`variants.stock\` не є доказом реально доступного товару. Підтвердити залишки в постачальника, оформити перерахунок і звірити всі незавершені резерви.
4. **Безпека:** персональні облікові записи, ролі, MFA, централізовані rate limits, моніторинг та незалежний аудит. Один спільний адмінтокен не підходить для команди.
5. **Дані:** версійні міграції Alembic, зашифроване резервне копіювання та регулярний тест відновлення. Поточний JSON-експорт недостатній.
6. **Операції та законодавство:** договір із доставкою, процедура повернень та фіскалізації, публічна оферта, політика приватності, документи продавця, консультація бухгалтера та юриста.
7. **Платежі:** автоматичної звірки банківської виписки немає; поточне ручне підтвердження в CRM не є перевіркою API банку, не виконувати дій із реальними грошима в staging.

## Перевірка staging

Створити pull request із гілки v9 в \`main\` у **draft**-стані. CI перевіряє код, API, сторінку аудиту, IBAN, безпечні перемикачі й Playwright на ізольованій БД.

Для ручного запуску в окремому середовищі, **не на виробничому Render**:

\`\`\`bash
export DATABASE_URL=sqlite:////tmp/beershop-v9-staging.db
unset BEERSHOP_PERSISTENT_DATABASE_URL
export BEERSHOP_ADMIN_TOKEN="REPLACE_WITH_LONG_RANDOM_STAGING_ONLY_SECRET"
export BEERSHOP_V9_DISABLE_ORDER_CREATION=1
export BEERSHOP_V9_REQUIRE_QUOTE_TOTAL=1
pytest -q tests/test_readiness_v9.py
\`\`\`

\`GET /api/admin/v9/readiness\` і діагностика схеми читають БД, але не змінюють ціни, склади, клієнтів, замовлення, платежі чи експортовані файли.

**Критерій випуску:** ніякого автоматичного merge або deploy на production за результатами цих тестів. Майбутній go-live потребує окремої перевірки всіх P0 ризиків, достовірних реквізитів, фізичних залишків, юридичних вимог і явного рішення власника.


## Етап 2 (staging) — мінімальні дозволи та тестове відновлення

**Обмежений аудиторський токен.** Оператор може **необов’язково** задати
\`BEERSHOP_V9_AUDIT_TOKEN\` (інший випадковий секрет від 32 символів). Він
надає **тільки** доступ до \`GET /api/admin/v9/readiness\`. Читання
замовлень, експорт персональних даних, склад і зміна цін із цим токеном
повинні отримати HTTP 401. Головний \`BEERSHOP_ADMIN_TOKEN\` залишається
тимчасовим повноправним секретом. Це **не MFA, не персональні облікові записи
і не повна рольова модель**; P0 security блокер не знято.

**Архів із контрольним маніфестом.** Захищений
\`GET /api/admin/maintenance/export\` зберігає формат v1, але додає
\`integrity\`: SHA-256 вмісту таблиць, схеми й кількості рядків.
Контрольна сума допомагає виявити **випадкові пошкодження**, але не
доводить автентичність, оскільки нападник із доступом до файлу може
перерахувати SHA-256. Архів містить **ПІБ, адреси, телефони й e-mail
покупців**. Зберігайте лише в зашифрованому приватному сховищі, не
надсилайте архів у чат і не кладіть у публічний GitHub.

**Перевірка без записів у робочу БД.** На окремому комп’ютері в корені
репозиторію, **без** \`DATABASE_URL\` та
\`BEERSHOP_PERSISTENT_DATABASE_URL\`, із локальним файлом архіву:

\`\`\`bash
env -u DATABASE_URL -u BEERSHOP_PERSISTENT_DATABASE_URL \
  python scripts/backup_rehearsal_v9.py /secure/private-backup.json

env -u DATABASE_URL -u BEERSHOP_PERSISTENT_DATABASE_URL \
  python scripts/backup_rehearsal_v9.py /secure/private-backup.json \
  --restore-to /tmp/beershop-v9-rehearsal-new.db
\`\`\`

Скрипт відхиляє архіви без v9-маніфесту, невідповідні схеми/контрольні
суми, сторонні колонки, некоректні FK під час відновлення та спробу
відновити **поверх існуючої** бази. Потрібний **новий** SQLite-файл у
каталозі тимчасових файлів; PostgreSQL/Neon заборонено як ціль.
Тестовий файл містить персональні дані архіву, тому його теж треба
шифрувати або безпечно видаляти після перевірки.

**Залишається необхідним:** незалежний справжній encrypted backup із
перевіркою збереження й відновлення, визначені RPO/RTO, відокремлені
привілеї, MFA, моніторинг, audit trail доступу. CI перевіряє лише
синтетичний архів; результати CI **не підтверджують можливість
відновлення даних Neon з реального архіву**.


## Швидка локальна перевірка з автоматичним очищенням (v9)

На відміну від команди \`backup_rehearsal_v9.py --restore-to\`, яка
залишає нову тестову БД на диску для ручного огляду, команда нижче за
замовчуванням **лише перевіряє цілісність архіву**, а з \`--rehearse\`
відновлює архів у випадковому тимчасовому каталозі й видаляє тестову базу
після перевірки:

\`\`\`bash
env -u DATABASE_URL -u BEERSHOP_PERSISTENT_DATABASE_URL \
  python scripts/verify_backup_v9.py /private/beershop-private-backup.json

env -u DATABASE_URL -u BEERSHOP_PERSISTENT_DATABASE_URL \
  python scripts/verify_backup_v9.py /private/beershop-private-backup.json --rehearse
\`\`\`

Виводяться **лише SHA-256, кількості таблиць/рядків і стан**, а не вміст
замовлень або особисті дані. Для пошкодженого архіву процес завершується
кодом 1. Не завантажуйте архіви в публічні сервіси. Тимчасова база містить
незашифровану інформацію під час тесту; ізоляція та шифрування самого
комп'ютера залишаються вимогою. Це не є тестом відновлення реальної Neon БД.


## Етап 3 — ізольована персональна авторизація, ролі та MFA

**Це лише opt-in staging-пілот.** Поки що старі адміністративні
\`/api/admin/*\` залишаються за спільним токеном. Персональні токени **не**
отримують доступ до старої CRM, цін, платежів, товарних правок,
експорту даних покупців чи банківських операцій. Отже повний P0-блокер
міграції RBAC **не закрито**.

Реалізовано окремий набір маршрутів \`/api/admin/v9/staff/*\`:
- \`POST /login\` — індивідуальний пароль **Argon2id** + шестизначний
  одноразовий код **TOTP**, із блокуванням акаунта після 5 невдач на 15 хв.
- \`GET /me\`, \`POST /logout\` — коротка 15-хвилинна сесія;
  на сервері зберігається тільки SHA-256 токена, він відкликається.
- \`GET /readiness\` — ролі \`owner\` і \`auditor\`;
  \`GET /catalog-summary\` — \`owner\`, \`catalog\`;
  \`GET /order-counts\` — \`owner\`, \`operations\`. У цих відповідях
  немає персональних даних покупців і функцій, що змінюють рахунки.
- \`GET /users\`, \`POST /users\`, \`POST /users/{id}/disable\` —
  тільки \`owner\`. Секрет TOTP повертається **лише один раз** під час
  створення нового користувача. Вимкнення користувача відкликає сесії.

MFA-секрети шифруються **Fernet** окремим ключем із середовища, що
**не зберігається в Neon/SQLite**. Не використовуйте для цього той самий
ключ, що й для основного адмінтокена; не передавайте ключі або TOTP URI
в чати, GitHub чи логи.

У тестовому середовищі, **лише з окремою локальною SQLite DB**
(синтетичні дані, ніяких production credentials):

\`\`\`bash
python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
# Отриманий ключ збережіть у власному менеджері секретів (не GitHub).
export DATABASE_URL=sqlite:////tmp/beershop-v9-staff-staging.db
unset BEERSHOP_PERSISTENT_DATABASE_URL
export BEERSHOP_V9_STAFF_AUTH=1
export BEERSHOP_V9_MFA_KEY='KEY_FROM_YOUR_PRIVATE_SECRET_MANAGER'
python scripts/bootstrap_owner_v9.py --username demoowner
\`\`\`

Команда запитує пароль локально без показу введеного тексту та
один раз виводить \`otpauth://\` URI для підключення MFA. Не зберігайте
його в історії чатів чи CI-логах. Після підготовки локального ізольованого
серверу відкрийте \`/staff-v9\` і введіть логін, пароль та код TOTP.
Інтерфейс має суворий CSP; сесія існує тільки в пам'яті вкладки.

При вимкненому \`BEERSHOP_V9_STAFF_AUTH\` всі нові staff-ендпоїнти і
сторінка повертають **503**. Жодні реальні акаунти чи секрети не створено;
не змінено Render/Neon.

**Перед запуском у production залишається:** незалежний security review,
інтеграція персональних ролей до *кожного* старого адмінендпоїнта,
вимкнення повноправного спільного токена, MFA recovery/rotation,
обмеження запитів за IP/мережею, моніторинг, процедури відкликання
і онбордингу, контрольована схема міграцій та ротація ключа Fernet.
Наявність staging-пілота не дозволяє приймати реальні платежі.


## Зовнішня CRM не потрібна: тільки BeerShop CRM

Власна **BeerShop CRM** є єдиною системою обліку клієнтів, замовлень
та менеджерів. Інтеграція KeyCRM залишена лише як застарілий код для
сумісності, але в суворому staging-режимі v9.1 усі шість маршрутів
KeyCRM вимкнені сервером (HTTP 503), включно з ручним підтвердженням
зовнішнього ID і передачею персональних даних. У розділах
**Операції 4.0** і **Інтеграції 4.1** старі контролі KeyCRM приховані;
відображається перехід до `/crm`. Нова пошта й банківські процеси
залишаються окремими напрямками; жодних реальних платежів або
зовнішніх запитів у тестах не проводиться.

Це **не видаляє історію та наявні дані** й не змінює production.
Перед майбутнім випуском потрібно окремо мігрувати старі інтеграції
та прибрати непотрібні змінні конфігурації й UI остаточно.

## v9.1 — охоплення старих API рольовим MFA (ізольований staging)

**Default OFF. Не вмикати на production.** Додано окремий захищений
перемикач для навчального/тестового середовища:
\`BEERSHOP_V91_ENFORCE_RBAC=1\`,
\`BEERSHOP_V91_STAGING_ACK=ISOLATED_STAGING_ONLY\`.
Одночасно має бути \`BEERSHOP_V9_STAFF_AUTH=1\`, окремий секрет
\`BEERSHOP_V9_MFA_KEY\` та **порожній**
\`BEERSHOP_PERSISTENT_DATABASE_URL\`. Якщо хоча б одна вимога
не виконується, старі захищені API відмовляють із HTTP 503,
**не повертаючись до старого адмінтокена**.

Коли увімкнуто strict-mode, всі маршрути старої адміністративної API
(\`/api/admin/*\`, CRM, каталог, склад, фінанси, операції, інтеграції,
експорт резервної копії) мають **серверну явну мапу дозволів**.
Невідомі маршрути **заборонені за замовчуванням (HTTP 403)**.
Колишній \`BEERSHOP_ADMIN_TOKEN\` та \`BEERSHOP_V9_AUDIT_TOKEN\`
не обходять MFA й права ролей.

| Роль | Доступ до старих API в strict-mode |
|---|---|
| \`owner\` | Усі явним чином дозволені адміністративні маршрути, зокрема резервний експорт |
| \`catalog\` | Назви/фото/категорії/запаси товарів; без перегляду CRM-клієнтів або цінової політики |
| \`operations\` | CRM та замовлення, логістика, читання залишків; без редагування валютної політики й ручних банківських підтверджень |
| \`finance\` | Фінансова політика, рахунки й підтвердження статусу оплати (тільки в ізольованому staging), читання замовлень; без CRM-клієнтів та експортів |
| \`auditor\` | Аудит готовності й технічна безпечна зведена звітність; без персональних даних та резервних копій |

Маршрути зміни закупівельної ціни (\`variants\`, масове застосування змін,
імпорт Prom.ua) тимчасово **owner-only**: змішана модель редагування
ціни та запасів ще не має безпечної польової перевірки прав.
Під час strict-mode навіть власнику **заборонено** зовнішні HTTP-запити
до KeyCRM/Нової пошти: ніякої відправки даних, звірки реального банку
чи синхронізації без окремого дозволеного середовища.

Вже існуючі індивідуальні MFA-сесії застосовуються до старих API.
Додатково:
- \`POST /api/admin/v9/staff/sessions/revoke-all\` — закриває **всі** власні сесії включно з поточною.
- \`POST /api/admin/v9/staff/users/{id}/revoke-sessions\` — власник негайно відкликає сесії працівника без вимкнення облікового запису.
- Окрема команда локальної перевірки приватної резервної копії:
  \`python scripts/verify_backup_v9.py /private/backup.json --rehearse\`.

**Залишається P0:** full UI routing для особистих токенів; централізовані
rate limits на кількох екземплярах; аудит безпеки; MFA recovery та
ротація encryption-key; версійні міграції; інструмент запланованих,
зашифрованих backup і перевірка відновлення Neon; юридична відповідність,
фізичний склад і справжня банківська звірка. Поточний архів містить
конфіденційні дані й **не зашифрований**. Ніяких реальних ключів або
платежів не використовувати.

Запуск тестів відбувається тільки в CI на **синтетичній** SQLite/PostgreSQL.
Продукційний Render і Neon не торкаємо. PR №17 залишається **Draft**.

## Етап v9.1.2 — персональний MFA-вхід до власної React CRM

У режимі `BEERSHOP_V91_ENFORCE_RBAC=1` разом із `BEERSHOP_V9_STAFF_AUTH=1`, підтвердженням `BEERSHOP_V91_STAGING_ACK=ISOLATED_STAGING_ONLY` і **відсутнім** `BEERSHOP_PERSISTENT_DATABASE_URL` сторінка `/crm/` показує **тільки персональний вхід**: логін, пароль Argon2id і шестизначний TOTP. Старий загальний токен не пропонується і не приймається сервером. Поза цим режимом незмінний старий вхід працює для чинного production, доки не буде окремого міграційного плану.

- Ролі `owner` і `operations` після перевірки MFA можуть переглядати й обробляти дані у **власній BeerShop CRM**, не в KeyCRM. Вхід перевіряє лише GET `/api/admin/crm/summary` і не створює/не індексує замовлення автоматично.
- Роль `operations` бачить склад, але не може змінити залишки, підтвердити оплату або запустити зовнішню синхронізацію доставки. UI приховує/вимикає дії; сервер окремо застосовує RBAC.
- Ролі `catalog`, `finance` та `auditor` **не допускаються до CRM**. Після відхилення входу токен негайно відкликається через `POST /api/admin/v9/staff/logout`; вони користуються обмеженою панеллю `/staff-v9`.
- Натискання виходу з React CRM стирає токен із пам'яті та робить best-effort запит серверного відкликання. Втрата мережі не гарантує доставку запиту — сесія має TTL максимум 15 хвилин, тому для термінового примусового завершення є `POST /api/admin/v9/staff/sessions/revoke-all` у панелі співробітника.
- `/staff-v9` показує посилання на нашу CRM для власника й операційної ролі, форму створення ролі `finance`, а також кнопку відкликання всіх власних активних сесій. Для повторного входу в іншій вкладці потрібен **новий TOTP-код** (успішні коди не можна використовувати вдруге).
- Ні `localStorage`, ні `sessionStorage`, ні cookies для токенів не використовуються; сесія живе тільки в пам'яті вкладки. Інтерфейс не замінює захист серверних API.

### Тести v9.1.2

`frontend/src/staffAuth.test.ts` перевіряє відсутність cookies та зовнішніх URL, відхилення недозволених ролей, відсутність обходу MFA, відкликання серверної сесії. `tests/crm_v91_staff_browser.cjs` запускається на синтетичному локальному fixture і перевіряє sign-in, GET-only під час входу, responsive 320–1366 px, обмеження керування банком/складом і logout/revoke. Головна CI також перевіряє стандартний вхід у CRM, щоб режим staging не зламав production.

**Не готово до реальних продажів:** потрібно повністю замінити shared-token у production, завершити персональні UX для фінансів і каталогу, додати централізоване throttling, відновлення MFA, надійний session/audit log, перевірити сторонні бібліотеки й секрети, шифрування бекапів та справжнє тестове відновлення Neon/PostgreSQL.


## v9.1.3 — захист від випадкового з'єднання staging із production

Сам `BEERSHOP_V91_STAGING_ACK` **не доводить ізоляцію БД**. Навіть
коли `BEERSHOP_V9_STAFF_AUTH=1`, персональний MFA-вхід і strict RBAC
тепер відмовляють (HTTP 503), якщо ініціалізований застосунок працює з
`BEERSHOP_PERSISTENT_DATABASE_URL`, віддаленим PostgreSQL/Neon або
невідомим типом БД. `/api/v91/features` не показує доступним
персональний CRM-вхід у такій конфігурації.

Тільки локальний SQLite дозволено за замовчуванням. Тестовий PostgreSQL
на `localhost`, `127.0.0.1` або `::1` додатково вимагає
`BEERSHOP_V91_ALLOW_LOCAL_POSTGRES=1`. Цей прапорець використовується
лише для ізольованої тестової БД у GitHub CI; не використовуйте його
в production або з локальним тунелем до Neon.

**Важливе обмеження:** локальний шлях SQLite чи адреса localhost самі
не гарантують синтетичний вміст БД. Додатково необхідні окремий проєкт,
ізоляція мережі та перевірка оператором. Це запобіжник, не завершений
security audit чи дозвіл на real sales. PR №17 залишається Draft.

### Обмеження ще на етапі старту застосунку

Перевірка ізоляції виконується **до** `migrate_once`, `create_all`,
`crm_backfill` і `inventory_backfill`, якщо ввімкнено staff MFA
або strict RBAC. Небезпечний URL завершує startup помилкою до будь-якого
з цих записів. Звичайний production-режим, де обидві функції вимкнені,
не змінюється.
