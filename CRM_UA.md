# BeerShop CRM 1.2 (платформа 4.4.0)

Вхід: `/crm` або посилання **BeerShop CRM** в `/manage`. Використовуйте чинний `BEERSHOP_ADMIN_TOKEN` із Render Environment. Не передавайте його в чат, URL, GitHub чи стороннім особам. У новій CRM токен живе лише в пам'яті вкладки; після перезавантаження потрібен повторний вхід.

## Поточні можливості

- Замовлення: пошук за номером, ім'ям, телефоном або email; фільтри статусу, оплати, пріоритету та відповідального; сторінки по 25 записів.
- Замовлення створюються на власній вітрині BeerShop і автоматично потрапляють у CRM разом із резервом в одній транзакції. Ручне створення в CRM прибрано. WordPress/WooCommerce не використовуються. Сервер перевіряє ціни, залишки й повторні запити.
- Обробка: Нове (`pending`) → Підтверджено (`confirmed`) → Комплектується (`picking`) → Виконано (`fulfilled`). Комплектування потребує підтвердженої оплати; завершення також потребує підтвердженої доставки. Оплата й доставка мають незалежні статуси.
- Склад: пошук за назвою/SKU, фільтри доступності й резерву, облікові кількості, відкриті резерви та останні 100 рухів для SKU. Перерахунок потребує підстави/документа, перевіряє поточний залишок і резерв та захищений від повтору.
- Клієнти: контакти, останні 100 замовлень і нотаток, редагування контактів із захистом від перезапису паралельних змін. Старі замовлення зберігають початкові контакти покупця.
- Відповідальні: довідник імен, призначення, деактивація. **Це не облікові записи, не ролі й не окремі дозволи.** Всі користувачі чинного токена мають повний адміністративний доступ.
- Нотатки не редагуються й не видаляються; повтор того самого запиту не створює дубль. Зміни статусу, відповідального, оплати та доставки потрапляють до журналу.
- Оплата: лише ручна звірка реальної банківської виписки, точної суми UAH, номера рахунку і унікального ID транзакції. Автоматичне підтвердження не вмикається.
- Доставка: запис вже створеної ТТН, перевірка офіційним API за наявності `NOVA_POSHTA_API_KEY` або ручне підтвердження за кабінетом перевізника. Відправлення не створюються. Завершення потребує оплати й доставки.
- Просте скасування дозволене лише до оплати та реєстрації ТТН. Повернення грошей/товару потребують окремого процесу, якого цей випуск не реалізує.

KeyCRM для власної CRM не потрібна. Наявні інтеграції залишено без зміни прапорців: `KEYCRM_SYNC_ENABLED=0`, `PRIVATBANK_READ_ENABLED=0`. Не вмикайте передачу даних або банківський доступ без належної авторизації.

## Дані й оновлення

### React 4.4

`/crm` тепер використовує React, TypeScript і Vite. API, структура бази, правила резервів, оплати та доставки не змінені. `/crm-legacy` зберігає попередній інтерфейс для оперативного повернення без міграції даних. Збірка включена в Docker; Node використовується лише під час складання, не як окремий сервер.

Вихід скасовує запити й прибирає дані сесії; запізніла відповідь не поверне стару картку на екран. Помилки API видимі у відповідному екрані або формі. Конфлікт версій контактів/залишків блокує повторне збереження старої форми: закрийте її, оновіть картку та звірте дані. Оплати й ТТН залишаються з явним підтвердженням перевірки, автоматичні дії не додані.

### Склад 4.3

`variants.stock` залишається **доступною до продажу кількістю**, яку використовують вітрина й старі редактори. Значення не переписуються при оновленні. Додаються `stock_reservations` і `stock_movements`; схема зафіксована в `migrations/0043_inventory.sql`.

Облікове «На складі» = доступно + відкритий резерв. Це не підтвердження фактичного перерахунку. Приклад: було 5; після замовлення 2 одиниць доступно 3, резерв 2, на складі 5. Створення ТТН нічого не списує. Після підтвердженого передання перевізнику доступно залишається 3, резерв стає 0, на складі 3. Скасування до оплати/ТТН звільняє резерв один раз.

Новий «Перерахунок» приймає фактичну кількість разом із резервом, а старі редактори каталогу змінюють лише доступну кількість. Обидва шляхи записують рухи з цієї версії. Перерахунок нижче резерву блокується. При розбіжності потрібна перевірка замовлень, а не автоматичне видалення резервів.

Історичні замовлення індексуються без повторного віднімання/повернення `stock`. Пропущені замовлення та завершення старою версією під час деплою звіряються при старті, вході й оновленні CRM; кількість у каталозі не змінюється. Історичні дати рухів не відновлюються: журнал фіксує час індексації. Відкат коду потребує повторної звірки перед користуванням складськими показниками; не видаляйте таблиці резервів.

API (чинний адмінтокен): `GET /api/admin/inventory`, `GET /api/admin/inventory/summary`, `GET /api/admin/inventory/{variant_id}`, `PATCH /api/admin/inventory/{variant_id}`. Коригування приймає `on_hand`, `expected_available`, `expected_reserved`, `reason`, `request_key`.

Підтверджений перевізником рух товару не підтверджує оплату. Автоматичні повернення товарів/коштів, часткові оплати, створення реальних ТТН, NovaPay та банківська автозвірка не активовані. Окремі працівники й права доступу залишаються наступним етапом.

### Базова CRM 4.2

Додаються лише `crm_customers`, `crm_managers`, `crm_order_details`, `crm_notes`. Каталог, SKU, ціни, залишки та попередні замовлення не переписуються під час деплою. PostgreSQL DDL зафіксовано в `migrations/0042_crm.sql`; поточний bootstrap `Base.metadata.create_all` створює еквівалентну схему. Повноцінна система версійних міграцій Alembic залишається окремим завданням.

Індексація історичних замовлень виконується при старті, вході та оновленні CRM. Дати, яких раніше не було в базі, не вигадуються. Нові замовлення й картки клієнтів створюються в одній транзакції.

Автоматичне зв'язування клієнтів потребує одночасного збігу нормалізованих email і телефону. Збігу лише телефону недостатньо. Зміна контактів може призвести до окремої картки при наступному замовленні зі старими контактами; автоматичного злиття немає.

Приватний резервний JSON у `/manage` включає нові таблиці. Це експорт із персональними даними, а не реалізований процес аварійного відновлення. Потрібні окремі перевірки відновлення, персональні входи/ролі, 2FA, політика зберігання даних, захист від зловживань і аудит безпеки перед реальними продажами.

## Перевірки

Спочатку `npm ci --prefix frontend` і `npm run build --prefix frontend`. `pytest -q` перевіряє API, авторизацію, транзакції, конфлікти версій, повторні запити, ізоляцію магазинів та міграцію зі старої схеми зі збереженням 100 товарів. Зовнішні провайдери в тестах заблоковані або замінені фікстурами. `npm test --prefix frontend` перевіряє клієнт API та завершення сесії.

`tests/crm_browser.cjs` запускається через Node із встановленим `playwright` і Chromium. Потрібен окремий локальний сервер із синтетичною базою та фіксованим тестовим курсом НБУ. Скрипт відмовляється працювати з нелокальним URL, створює лише локальні фікстури та не звертається до провайдерів. Параметри: `CRM_TEST_URL`, `CRM_TEST_TOKEN`, `CHROMIUM_PATH`. Покрито оформлення на власній вітрині, автоматичне надходження в CRM, резерв, призначення, екранування нотаток, ручні оплату/доставку, комплектування/завершення, перерахунок складу, контакти, пошук і ширини 1366/390/320 px. GitHub CI запускає API-тести на SQLite і PostgreSQL 16.

Локальний сервер-фікстура (окремий термінал, порожній тимчасовий файл БД; тестовий токен не використовувати на Render):

```bash
env -u BEERSHOP_PERSISTENT_DATABASE_URL PYTHONPATH=. DATABASE_URL=sqlite:////tmp/beershop-crm-browser.db BEERSHOP_ADMIN_TOKEN=tttttttttttttttttttttttttttttttttttttttt uvicorn crm_preview:app --app-dir tests --host 127.0.0.1 --port 8018
```

Потім `node tests/crm_browser.cjs` та `node tests/crm_react_browser.cjs`. Chromium встановлюється командою `npx --prefix frontend playwright install chromium`, або шлях передається через `CHROMIUM_PATH`. Скриншоти зберігаються в `/tmp/crm-*.png` і `/tmp/inventory-*.png`. Додатковий React-сценарій перевіряє запізнілі відповіді, повільний довідник, фокус/Escape, конфлікт залишків, помилки/повтор, вихід і 401. GitHub CI запускає обидва браузерні сценарії на ізольованій SQLite через `python tests/run_crm_browser.py` та зберігає скриншоти.

Жодних тестових покупців, оплат або ТТН у live-середовище не додається.
