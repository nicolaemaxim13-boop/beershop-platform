# BeerShop 4.1.1: інтеграції та перевірка

## Стан підключення

Код використовує офіційні HTTPS API. Реальні запити потребують ключів у Render.
Під час розробки використовуються лише штучні замовлення в окремій SQLite-базі
та імітовані відповіді API. У робочій базі тестові замовлення не створюються.
Міграції схеми для цього оновлення не потрібні: результати звірки зберігаються
в наявному operations_audit, зв'язки та доставка в order_operations.
Таблиці products, variants і categories інтеграції не змінюють.

## Render

Сервіс: beershop-preview, гілка main, Dockerfile у корені,
health check /api/health, один інстанс. Автодеплой увімкнений на commit.
Після merge не запускайте другий деплой вручну.

Поточний render.yaml описує початкове створення preview з Render Postgres.
Це не повний опис перенесення на Neon. Не застосовуйте його для повторного
створення інфраструктури. Чинне підключення Neon задається секретною змінною
BEERSHOP_PERSISTENT_DATABASE_URL; код надає їй пріоритет над DATABASE_URL.
Мітка _beershop_migration_info запобігає повторному копіюванню після перезапуску.
Не змінюйте URL бази та не запускайте імпорт каталогу для підключення API.

Змінні задаються в Dashboard → beershop-preview → Environment:

| Змінна | Призначення |
| --- | --- |
| KEYCRM_API_KEY | Секретний ключ KeyCRM |
| KEYCRM_SYNC_ENABLED | 0 за замовчуванням; 1 лише після дозволу на передачу даних покупців |
| NOVA_POSHTA_API_KEY | Секретний ключ API Нової пошти |
| PRIVATBANK_STATEMENT_TOKEN | Токен Автоклієнта з дозволеним доступом до виписок |
| PRIVATBANK_READ_ENABLED | 0 за замовчуванням; 1 дозволяє лише перевірку settings |

Значення секретів не додаються в GitHub, браузерний код або чат.
Після збереження змінних потрібен успішний деплой. Адміністратор може побачити
лише ознаки налаштованих ключів у вкладці «Інтеграції 4.1».
Наявність ключа ще не означає підтверджену авторизацію провайдера.

## KeyCRM

Офіційна специфікація: https://docs.keycrm.app/api.yaml

- GET /v1/order/source: джерела замовлень, без даних покупців.
- POST /v1/order: лише після KEYCRM_SYNC_ENABLED=1, авторизації адміністратора
  та підтвердження SEND_PERSONAL_DATA_TO_KEYCRM для конкретного замовлення.
- GET /v1/order/{orderId}?include=status: звірка ID, source_id і source_uuid.

source_uuid має вигляд BS-000001. Перед POST зберігається резервування в БД;
після тайм-ауту повторний POST блокується, адже запис міг бути створений у CRM.
Знайдіть замовлення в CRM, введіть його числовий ID та правильне джерело,
натисніть «Звірити замовлення і статус KeyCRM». Невідповідність будь-якого
ідентифікатора забороняє прив'язку. Звірка також закриває неоднозначну спробу.

Статус CRM зберігається як окремий status_id у журналі. Користувацькі ID
статусів не перетворюються на локальне скасування або оплату. Це запобігає
випадковому поверненню складських залишків чи підтвердженню надходження коштів.

## Нова пошта

Офіційна документація: https://developers.novaposhta.ua/documentation
Endpoint: https://api.novaposhta.ua/v2.0/json/

Використовується виключно TrackingDocument/getStatusDocuments для існуючої
14-значної ТТН. Телефон, ім'я та адреса покупця не передаються. Методи створення
чи редагування відправлень відсутні. Перевіряються success, структура відповіді
та точний збіг номера ТТН; персональні поля відповіді відкидаються.

Перегляд ТТН не змінює локальні дані. Окрема команда синхронізації зберігає
стан доставки та запис аудиту. Код 1 відповідає created; 4, 5, 6, 7, 8, 41, 101
відповідають handed_over; 9, 10, 11 відповідають delivered. Невідомі коди,
відмови, повернення та регрес стану вимагають ручної перевірки. Оплата і статус
самого замовлення не змінюються навіть після delivered.

Під час перевірки 2026-11-06 портал документації Нової пошти повертав HTTP 403.
Live-перевірка ключа та відповідності кодів на дозволеній існуючій ТТН залишається
обов'язковим кроком перед операційним використанням; тестові ТТН у live API не надсилаються.

## ПриватБанк

Офіційне підтвердження API виписок:
https://privatbank.ua/business/intehratsiya

Документація Автоклієнта, на яку посилається банк:
https://docs.google.com/document/d/e/2PACX-1vTtKvGa3P4E-lDqLg3bHRF6Wi9S7GIjSMFEFxII5qQZBGxuTXs25hQNiUU1hMZQhOyx6BNvIZ1bVKSr/pub

Передбачено лише GET https://acp.privatbank.ua/api/statements/settings
з заголовками token та Content-Type: application/json;charset=utf8.
SUCCESS підтверджує доступ до settings, але НЕ право читати конкретний рахунок.
phase=WRK і work_balance=N означають готовність API до запитів.
statements_access_verified залишається false. Виписки не завантажуються.

Майбутнє читання виписок потребує дозволу власника рахунку, прив'язки до
визначеного IBAN, повної пагінації та звірки суми, валюти, точного номера
рахунку замовлення, напрямку й остаточного стану операції. Документація банку
визначає REF+REFN для унікальності платіжної інструкції. Потрібно також
обробляти повернення, часткові платежі та повторне отримання тієї самої виписки.
Автоматичного підтвердження оплат у цій версії немає.

## Перевірка

Запускайте тести лише з окремою тестовою DATABASE_URL та без
BEERSHOP_PERSISTENT_DATABASE_URL. Провайдерні HTTP-запити заблоковані fixture;
кожна транспортна перевірка встановлює власний mock.

```sh
pytest -q
python -m compileall -q app
node --check web/connectors41.js
```

Перед і після деплою звіряйте кількість та контрольний відбиток products і
variants read-only SQL-запитами; каталог має містити всі 100 товарів і 100 SKU.
Перевірте статус live конкретного commit у Render, /api/health, /, /manage,
каталог та відмову 401 для неавторизованого доступу до інтеграцій.
