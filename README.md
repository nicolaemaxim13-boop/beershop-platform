# BeerShop 4.4: власна CRM 1.2 на React

**Валютне ціноутворення:** [PRICING_UA.md](PRICING_UA.md) — ручні курси ПриватБанку/обмінника, податки, комісії та прибуток, активація тільки після перевірки курсів.


Робоча область: `/crm`. Замовлення надходять лише з власної вітрини; ручне створення в CRM прибрано. Додано окремий складський резерв, журнал рухів, перерахунок та етап «Комплектується». Клієнти, відповідальні, нотатки, контрольовані ручні оплати й доставка збережені. Докладно: [CRM_UA.md](CRM_UA.md). WordPress/WooCommerce не використовуються, KeyCRM не потрібна. Персональні акаунти й ролі ще не реалізовані; система залишається preview.

CRM перенесено на React + TypeScript + Vite (`frontend/`). Вітрина, Python/FastAPI, SQLAlchemy та PostgreSQL залишаються без зміни бізнес-логіки. Збірку віддає той самий Python-сервер; додатковий Node-сервер чи платний сервіс не потрібен. Попередній інтерфейс доступний у `/crm-legacy`. Опис розробки: [frontend/README.md](frontend/README.md).

Нижче збережено історичні описи попередніх випусків; поточні інтеграційні обмеження див. також у [INTEGRATIONS_UA.md](INTEGRATIONS_UA.md).

## BeerShop Admin 3.0 (історичний опис)

На основі BeerShop 2.1. Додано редагування товарів, завантаження JPEG/PNG/WebP, попередній перегляд та імпорт Prom.ua CSV, журнал імпортів. Адмінпанель — `/manage`.

## Запуск

```bash
pip install -r requirements.txt
npm ci --prefix frontend
npm run build --prefix frontend
export BEERSHOP_ADMIN_TOKEN="$(python -c 'import secrets; print(secrets.token_urlsafe(40))')"
uvicorn app.main:app --reload
```

Відкрийте http://localhost:8000/manage. Імпортуйте CSV у вкладці «Prom.ua → BeerShop» після попереднього перегляду. Для першого запуску краще використовувати чисту базу даних.

**Увага:** У вихідному CSV є ціни у UAH та USD. USD зберігаються без автоматичної конвертації та не допускаються до оформлення замовлення, доки не буде погоджена ціна у гривнях. CSV не містить достовірних числових залишків, тому нові варіанти отримують stock=0, а значення наявності, відмінні від `+`, приховуються. Після імпорту відредагуйте залишки в адмінпанелі. Відсутні у файлі товари не видаляються. Повторний імпорт оновлює дані, тому для подальшого ручного керування не повторюйте імпорт без потреби.

## Обмеження

Не готово до production: потрібні міграції Alembic, рольова авторизація замість одного токена, аудит змін, резервні копії БД і фото, зовнішнє файлове сховище, перевірка зображень декодером, захист від зловживань, журнал платежів, тести конкурентних операцій і аудит безпеки. Папка `uploads` має бути на постійному диску, інакше фото можуть зникнути після redeploy. Система не розгорнута в інтернеті.

## BeerShop Admin 3.1 — масове редагування

Відкрийте `/manage` → **Масовий редактор**. Пошук за назвою або SKU, фільтри за категорією, публікацією та валютою. Зміна цін, валюти, залишків і доступності SKU. **1. Переглянути зміни → 2. Зберегти**. Сервер звіряє вихідні значення та зберігає пакет однією транзакцією. Максимум 100 SKU за операцію, 25 на сторінку.

Серверні маршрути (потрібен `BEERSHOP_ADMIN_TOKEN`):
- `GET /api/admin/bulk/catalog`
- `POST /api/admin/bulk/preview`
- `POST /api/admin/bulk/apply`

**Без автоматичної конвертації USD → UAH.** Для зміни валюти потрібно подати перевірену нову ціну. Жоден раніше імпортований товар цим оновленням автоматично не змінюється.

Обмеження: немає окремих акаунтів працівників, журналу аудиту, міграцій БД, постійного сховища фото та production-перевірки безпеки. Render Free PostgreSQL має 30-денний термін дії. Це тестова платформа, не для реальних оплат.


## BeerShop Admin 3.2 — мобільний каталог

У /manage оберіть **Каталог 3.2** після входу за адміністративним токеном. Доступні пошук товарів за назвою/SKU, фільтр категорії, сторінки по 20 позицій, редагування назви, опису, категорії, публікації, постійного HTTPS-посилання на фото, створення і перейменування категорій. Slug категорії не змінюється, щоб не ламати посилання.

Фото можна завантажити з телефону через існуючий API, але **локальні uploads на Render Free тимчасові** й можуть зникнути після перезапуску. Для постійних фото потрібне зовнішнє файлове сховище; краще поки використовувати перевірений HTTPS URL.

Ціни й залишки змінюються в **Масовому редакторі**, щоб не допустити автоматичної конвертації USD в UAH. Жоден імпортований товар не змінюється автоматично при деплої цієї версії.

Обмеження: один адмінтокен замість ролей і 2FA, немає надійних резервних копій і міграцій схеми, немає продакшн-аудиту безпеки. **Не приймайте реальні замовлення чи платежі** до завершення цих робіт.

## BeerShop 3.3 — окрема постійна БД та резервне копіювання

На Render зберігається попередня база `DATABASE_URL` (джерело). Нову незалежну Neon БД передавайте тільки через секретну змінну середовища `BEERSHOP_PERSISTENT_DATABASE_URL` — **ніколи не додавайте URL із паролем у GitHub**.

Перший деплой із цією змінною створює таблиці в порожньому Neon, читає всі таблиці Render у порядку зовнішніх ключів, копіює ID, ціни, товари, категорії, склади, історію імпорту та замовлення (з персональними даними), звіряє кількості, оновлює PostgreSQL sequence й записує міграційний маркер в одній транзакції. Якщо Neon містить незареєстровані дані або перевірка не проходить, новий деплой завершується помилкою, залишаючи стару версію та Render БД незмінними. Наступні рестарти не перезаписують Neon.

Після успішного переключення у `/manage` → **Резервні копії** можна перевіряти кількість записів та завантажувати повний приватний JSON експорт (включно із замовленнями). Зберігайте його **зашифрованим** у приватному сховищі, не публікуйте та не надсилайте в чат. Запит потребує адмінтокена. Сам експорт не є автоматичною хмарною резервною копією; імпорт із такого JSON ще не реалізований.

На безкоштовному Render завантажені в локальну папку фотографії можуть зникати після деплою. Neon переносить лише посилання на фото, а не їхні локальні файли. Постійне об'єктне сховище необхідно підключити окремо.

**Тестова система, не для реальних продажів**: немає ролей, 2FA, автоматичних регулярних бекапів/відновлення, повних міграцій Alembic і перевірки конкурентних замовлень.

## BeerShop 3.4 — курс USD/UAH та ціни в гривнях

Офіційний курс НБУ отримується з https://bank.gov.ua/NBUStatService/v1/statdirectory/exchange?valcode=USD&json. Сервер перевіряє курс за зверненням до каталогу/кошика з кешуванням до 2 годин і зберігає останню перевірку в Neon (таблиця fx_states). Якщо API не працює, система може використовувати перевірений курс до 96 годин за умови прийнятної дати курсу. За відсутності актуального курсу повертається HTTP 503 — замовлення не створюються.

Базові SKU, їхня початкова ціна та валюта залишаються без змін. Для позицій USD гривнева ціна дорівнює базовій USD × курс НБУ. Для позицій UAH гривнева ціна = базова UAH × поточний курс / базовий курс на момент першої успішної перевірки. Базовий курс фіксується один раз і не перезаписується. Отже, **усі 100 позицій** будуть індексовані на USD, але вітрина показує **UAH**. Округлення до копійок ROUND_HALF_UP.

API: GET /api/fx/usd-uah; GET /api/products (ціни UAH й окремо source_price/source_currency); POST /api/quote (поточна ціна та залишки); POST /api/orders (необов'язковий expected_total для захисту від зміни курсу). Покупець підтверджує нову суму, якщо курс змінився, а після створення замовлення його сума фіксується в гривнях.

НБУ — офіційний, не комерційний курс продажу USD; додаткову маржу та фінансову політику необхідно налаштувати окремо. Для продажів також потрібні фактичні складські залишки, оплати та заходи безпеки.

## BeerShop 4.0 — операційний центр (перший етап)

В адмінпанелі /manage → **Операції 4.0** доступні:
- зведення за замовленнями, оплаченими та неоплаченими рахунками, CRM, ТТН;
- **ручне** підтвердження IBAN-платежу тільки після звірки банківської виписки з унікальним ID транзакції, сумою в UAH і призначенням `BS-XXXXXX`; одна транзакція не може оплатити два замовлення;
- підготовка **попереднього JSON** для KeyCRM з source_id/source_uuid, покупцем, SKU, кількістю та зафіксованими в UAH цінами, а потім ручний запис фактичного зовнішнього ID;
- реєстрація **вже створеної** ТТН Нової пошти та переходи статусів created → handed_over → delivered тільки після ручної перевірки;
- журнал перевірок і змін для конкретного замовлення.

**Жоден банк, KeyCRM чи Нова пошта ще не підключені через API.** Жодна автоматична операція з оплатою, відправленням, складом стороннього сервісу або фіскалізацією не виконується. Підтвердження в цьому модулі означає лише, що адміністратор заявив про перевірку зовнішнього документа, а не криптографічно підтверджену відповідь банку/CRM/перевізника.

Legacy API `PATCH /api/admin/orders/{id}/payment` більше не дозволяє переводити замовлення в `paid` без підтвердження через операційний модуль. Статус `fulfilled` можна встановити лише після підтвердженої вручну оплати й доставки.

Усе розгортання **без автоматичної зміни 100 товарів або попередніх замовлень**. Додаються таблиці `order_operations` і `operations_audit`. Старий механізм export JSON повністю включає їх.

Щоб підключити реальні інтеграції пізніше, знадобляться API KeyCRM, дозволений банківський API ФОП, Нова пошта, належні договори та тестовий сценарій. Токени — тільки в секретних змінних Render, не в GitHub і не в чаті. У розділі оплат передбачено виключно IBAN; рішення щодо РРО/ПРРО окремо перевіряється з українським бухгалтером/податковим консультантом. **Платформа поки не готова до реальних продажів.**

## BeerShop 4.1 — provider integrations (opt-in)

Це перша інтеграційна версія: KeyCRM (читання джерел, ручне API-відправлення замовлення), Нова пошта (читання статусу вже створеної ТТН) та видимий статус ПриватБанку (автоматична звірка не реалізована). Код не відправляє гроші, не створює ТТН і не змінює локальні статуси доставки на підставі однієї відповіді API.

Налаштування на **Render → BeerShop → Environment**:
- `KEYCRM_API_KEY` — приватний ключ KeyCRM. Без нього можливість лише підготовки JSON у вкладці «Операції 4.0».
- `KEYCRM_SYNC_ENABLED=1` — **окрема явна активація** фактичного відправлення даних покупців до KeyCRM. За замовчуванням вимкнено. Вимикайте, якщо потрібний режим тільки читання.
- `NOVA_POSHTA_API_KEY` — приватний ключ Нової пошти; дозволяє лише отримувати статус наявної ТТН.
- Для ПриватБанку **немає токена в цій версії**: автоматичний банк-процес не активований без перевіреної схеми API, дозволів і банківської документації.

Перед відправленням замовлення KeyCRM відкрийте у CRM окреме джерело BeerShop та оберіть його ID в «Інтеграції 4.1». Адміністратор натискає кнопку відправлення та підтверджує передачу персональних даних. Сервер формує один `POST /order` з `source_id`, стабільним `source_uuid`, покупцем та зафіксованими гривневими цінами. **Перед зовнішнім викликом** створюється `crm_dispatches` із станом `needs_reconciliation`. Після відповіді з ID замовлення стан переходить у `confirmed`. Якщо сталася помилка/timeout, повторні POST заблоковані до ручної перевірки CRM і запису фактичного ID у «Операції 4.0», тоді статус — `reconciled`. Це консервативна модель захисту від дублікатів, яка іноді вимагає ручного втручання.

Офіційні API:
- KeyCRM: https://docs.keycrm.app/ та https://help.keycrm.app/uk/process-automation-api-and-more/how-to-configure-the-order-transfer-script-in-keycrm
- Нова пошта: https://novaposhta.ua/for-business/cooperation/integration/
- ПриватБанк: https://privatbank.ua/business/intehratsiya

API BeerShop (всі маршрути нижче вимагають `BEERSHOP_ADMIN_TOKEN`):
- `GET /api/admin/connectors41/status`
- `GET /api/admin/connectors41/keycrm/sources`
- `GET /api/admin/connectors41/keycrm/dispatch/{order_id}`
- `POST /api/admin/connectors41/keycrm/sync/{order_id}`
- `GET /api/admin/connectors41/nova-poshta/tracking/{order_id}`

**Примітка з безпеки:** немає автоматичного фонового циклу синхронізації, webhook verification, автоматичного reconciliation, обробки повернень коштів, ролей співробітників і 2FA. KeyCRM лімітує запити 20/хв; код застосовує локальну паузу понад 3 с між KeyCRM запитами в межах процесу. Не вводьте API-ключі в чат або GitHub. Виробничу експлуатацію дозволяти лише після перевірки обробки ПД, фіскалізації, банківських відповідей і резервного відновлення.
